\section{Зэрэг захиалгын туршилтын үр дүн}

\text Ижил хугацаанд, нэг өрөө рүү олон хэрэглэгч нэгэн зэрэг захиалга өгөх үед систем давхар захиалга үүсгэхээс бүрэн сэргийлэх чадварыг шалгав.

Хэрэгжүүлэлт: Захиалга үүсгэх үйл явцад Prisma үйлчилгээний transaction дотор PostgreSQL-ийн түгжээг (пессимист түгжээ буюу \texttt{SELECT ... FOR UPDATE}) ашигласан ба давхар баталгаажуулалт хийх зорилгоор өгөгдлийн санд огнооны давхцлыг хориглох EXCLUDE хязгаарлалт тавьсан.

1. Prisma гүйлгээ доторх пессимист түгжээ:

\begin{lstlisting}[language=SQL, caption={Захиалга үүсгэхийн өмнө өрөөг түгжих (SELECT ... FOR UPDATE)}, label={lst:pessimistic-lock}]
-- Transaction эхлүүлэх
BEGIN;

  -- Өрөөг түгжих
  SELECT id, room_id, check_in, check_out
  FROM   bookings
  WHERE  room_id  = :roomId
    AND  check_in  < :checkOut
    AND  check_out > :checkIn
  FOR UPDATE;           -- бусад хэрэглэгч энэ мөрийг хүлээнэ

  -- Хэрэв давхцал олдвол алдаа буцаана, олдохгүй бол шинэ захиалга нэмнэ
  INSERT INTO bookings (room_id, user_id, check_in, check_out, status)
  VALUES (:roomId, :userId, :checkIn, :checkOut, 'PENDING');

COMMIT;
\end{lstlisting}

2. EXCLUDE хязгаарлалт (давхцлыг өгөгдлийн сангийн түвшинд хаах):

\begin{lstlisting}[language=SQL, caption={Bookings хүснэгтэд огнооны давхцлыг хориглох EXCLUDE constraint}, label={lst:exclude-constraint}]
-- Prisma migration дотор raw SQL ашиглан тавьсан constraint
ALTER TABLE bookings
  ADD CONSTRAINT no_double_booking
  EXCLUDE USING gist (
    room_id   WITH =,                      -- ижил өрөө
    daterange(check_in, check_out) WITH &&  -- огноо давхцах үед
  );

-- Давхцсан тохиолдолд PostgreSQL автоматаар дараах алдааг буцаана:
-- ERROR: conflicting key value violates exclusion constraint
--        "no_double_booking"
\end{lstlisting}

Туршилтын арга: Нэгэн зэрэг $N=\{5, 20, 50\}$ хэрэглэгч яг ижил \texttt{room\_id} болон огноонд захиалга өгөх хүсэлтийг (POST хүсэлт) илгээж, туршилтыг тус бүр 10 удаа давтан хийв.

Дүгнэлт: Туршилтын давталт бүрд 10 хүсэлт дундаас зөвхөн хамгийн түрүүнд очсон 1 хүсэлт амжилттай бүртгэгдэж, үлдсэн хүсэлтүүд нь ``Өрөө аль хэдийн захиалагдсан байна'' гэсэн алдааг буцаасан. Энэ нь систем зэрэг хандалтад найдвартай ажиллаж, давхар захиалга үүсэх эрсдэлийг 0 хүртэл бууруулсныг баталж байна. Хүсэлт ихсэх үед мэдээллийн санд түгжээ хүлээгдэх хугацаа уртасч, хариу өгөх хугацаа нэмэгдэж байгаа нь пессимист түгжээний хүлээгдэж байсан зан төлөвтэй бүрэн нийцэж байна.

\section{End-to-End захиалгын урсгалын туршилтын үр дүн}

Хэрэглэгчийн бодит туршлагыг шалгахын тулд Playwright ашиглан системийн бүрэн урсгалыг (8 алхамтай) автоматжуулсан тестээр шалгасан:
\begin{enumerate}
    \item Системийн нүүр хуудасруу хандах
    \item Огноо болон хүмүүсийн тоог сонгох
    \item Боломжит өрөөний мэдээллийг харах
    \item Тухайн сувиллаас санал болгож буй багцыг сонгох
    \item Хэрэглэгчээр нэвтэрч захиалгыг \texttt{PENDING} төлөвтэй үүсгэх
    \item Өөр цонхоор Админ/Ажилтнаар нэвтрэн захиалгыг \texttt{CONFIRMED} төлөвтэй баталгаажуулах
    \item Имэйл мэдэгдэл илгээгдсэн эсэхийг шалгах
    \item Захиалга статистик дашбоард руу шууд нэмэгдсэн эсэхийг баталгаажуулах
\end{enumerate}

Эдгээр бүх алхмуудын нийт гүйцэтгэлийн хугацаа (end-to-end execution time) дунджаар 6.2 секунд болсон. Invariant шалгалтын хувьд \texttt{created\_at < confirmed\_at} зэрэг timestamp-үүдийн дараалал бүрэн зөв байж, систем доторх урсгалын гацаа (bottleneck) үүсээгүйг давхар баталсан.

\section{Судалгааны асуултуудын хариу}

\textbf{RQ1-ийн хариу:} §3.2-т тогтоосон 15 минутын суурь үзүүлэлтээс §4.4-т хэмжсэн шинэ системийн 2.3 минут хүртэл ($\sim$85\% бууралт) нэг захиалга боловсруулах хугацаа эрс буурсан нь баталгаажсан. Мөн тайлан гаргах хугацаа 35 минутаас 1.2 минут хүртэл (96.6\%), өрөөний хүртээмжийн шалгалт 2.8 минутаас 0.2 минут хүртэл (92.9\%) тус тус буурснаар k6 туршилтын p95 хариу хугацаа 278--816\,ms хязгаарт (Хүснэгт~\ref{tab:k6-results}) багтаж байгаа нь шинэ систем хэрэглэгч болон ажилтнуудын үйл ажиллагааны үр ашгийг мэдэгдэхүйц нэмэгдүүлсэн гэж дүгнэх боломж олгоно.

\textbf{RQ2-ын хариу:} Концуррент туршилт (Хүснэгт~\ref{tab:concurrency-test})-ийн 10 давталтын бүрд зөвхөн нэг хүсэлт амжилтанд хүрч, давхар захиалга үүсэх тохиолдол 0 (0\%) байсан. Энэ нь PostgreSQL-ийн pessimistic locking (\texttt{SELECT ... FOR UPDATE}) болон EXCLUDE constraint-ийн хослол нь хүний алдаанаас шалтгаалсан давхардлыг хатуу урьдчилан сэргийлж байгааг практикт баталгаажуулсан.

\textbf{RQ3-ын хариу:} §4.7-ийн SUS үнэлгээгээр систем нийт 76.3 оноо ($SD=8.4$, $n=13$) авч, Bangor нарын \cite{bangor2008sus} 68 онооны босго үзүүлэлтээс мэдэгдэхүйц давсан ба ``Сайн'' (Good) ангилалд хамрагдсан. Ажилтнуудын дундаж 81.7 оноо нь админ интерфейс хэрэглэхэд хялбар байсныг илтгэж байна.

\section{Дүгнэлт ба цаашдын чиглэл}

Энэхүү судалгааны ажлаар уламжлалт хэлбэрээр явагддаг сувиллын газруудын бүртгэл мэдээлэл, захиалгын үйл явцыг бүрэн цахимжуулж, орчин үеийн Next.js, Prisma, PostgreSQL технологиудыг ашигласан реактив веб системийг хөгжүүлэн нэвтрүүлж туршлаа. Судалгааны үр дүнгээс дүгнэхэд:
\begin{enumerate}
    \item Цахим систем нь ажилтнуудын өдөр тутмын гар ажиллагаатай холбоотой цаг үрэлтийг дунджаар 70--90\% бууруулж чадсан.
    \item Мэдээллийн санд concurrency control аргачлалыг тусгаснаар давхар захиалга буюу өрөөний зөрчил гарах эрсдлийг бүрмөсөн шийдэж чадсан.
    \item Хэрэглэгчдийн дунд явуулсан үнэлгээгээр системийн ашиглахад хялбар байдал өндөр буюу 76.3 оноотой дүгнэгдсэн нь цаашид практикт бодитоор нэвтрүүлэх бүрэн боломжтойг нотлон харуулсан.
\end{enumerate}

Цаашдын чиглэл: Системийг улам боловсронгуй болгохын тулд гар утасны аппликейшн хөгжүүлэх, олон сувиллын түрээсийн (SaaS) өргөтгөлийн боломжуудыг нэмэх бүрэн боломжтой байна. Түүнчлэн, захиалгын урьдчилгаа төлбөр тооцооны системийг Монголын банкуудын QPay болон SocialPay үйлчилгээнүүдтэй шууд холбох интеграци хийж, захиалга баталгаажсан тухай мэдэгдлийг гар утасны SMS-ээр давхар илгээдэг болбол үйлчилгээний чанар илүү сайжрах боломжтой байна.
